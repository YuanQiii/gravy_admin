# AI 工程化资产落地手册

面向**新项目 Day 0**，以及**存量项目上的增量开发**（见第 6 节）。内容分六部分：实现流程、提示词库、最小模板、维护提示词、反面清单、棕地适配。

配套阅读：[`ai-engineering-system-audit-2026-09-11.md`](ai-engineering-system-audit-2026-09-11.md)（本仓库资产层实测审计，本手册的教训来源）。

---

## 0. 使用说明

**三分钟上手**：把 [P0 提示词](#p0--资产骨架一键生成) 复制给 AI，它会一次建出除 `openspec/` 外的全部资产骨架（`openspec/` 用 `openspec init` 生成，见步骤 4）；然后按 P1 → P6 顺序逐个填实。

**提示词约定**：

- `<尖括号>` 是需要你替换的占位符。
- 每条提示词都自带验收标准，产出不符合就让它返工，别自己动手改。
- 提示词设计遵循一个原则：**先读再写、只建骨架不编内容、索引路径必须真实存在**。

**执行主体**：只有 4 处需要人主导判断（准备输入、领域词汇确认、ADR 决策、评审），其余交给 AI + 门禁。

### 0.1 资产分类：哪些是 AI 专属，哪些只是被 AI 消费

本手册列出的六份资产**并非都属于"AI 工程化"**。混为一谈会导致一个实际后果：把通用工程实践的维护错误地挂在"AI 相关工作"上，于是没人管。正确的区分是：

| 资产 | 来源 | 属性 | 更新由什么触发 |
| --- | --- | --- | --- |
| `AGENTS.md` + 工具薄指针 | AGENTS 开放标准（Agentic AI Foundation / Linux Foundation） | **AI 专属**（AI 出现前不存在此物） | AI 工具变更、规则变更 |
| `.agents/` 按需知识库 | AGENTS 标准中的工具配置目录约定 | **AI 专属** | 主题规则变更 |
| `hermes/` 经验库 | 项目自定 | **AI 导向**（内容面向 AI 消费） | 变更归档后回填 |
| `CONTEXT.md` 领域词汇 | **DDD 通用实践**（Eric Evans, 2003 的 ubiquitous language） | 通用 | 新概念进代码前 |
| `docs/adr/` | **通用工程实践**（Michael Nygard, 2011） | 通用 | 做出不可逆决策时 |
| `openspec/` 规格 | 规格驱动开发理念；OpenSpec 是 AI-native 实现 | 半通用 | verify 通过后 sync |
| CI 门禁 | 通用工程实践 | 通用 | 持续收紧 |

**关键结论**：`docs/adr/`、`CONTEXT.md`、CI 门禁**不是因为使用 AI 才产生的** —— 它们在 AI 之前的二十年工程实践中就已存在，AI 只是为它们**增加了第二个消费者**（AI 需要知道"为什么这么决定"，才不会反复重开已决事项）。

因此这三者的更新触发点是**工程活动**（做了决策、改了规则、改了代码），不是 AI 活动。把它们当成"AI 资产"来安排维护，是分类错误。

## 1. 实现流程

### 步骤 0 · 准备输入（人工，约 10 分钟）

先想清楚三件事，写下来作为 AI 的输入：

1. **技术栈与目录结构** —— 已确定的，不要边建边改。
2. **一句话业务定位** —— 用于 AGENTS.md 的"项目概况"。
3. **3~5 个最容易混的领域概念** —— 例如"客户 vs 用户""访客 vs 游客"这种团队日常会混用的词。这是 `CONTEXT.md` 的唯一输入，也是最容易被跳过的一步。

> **为什么这步不能省**：领域词汇是后面所有文档的用词基准。等写完一堆文档才发现术语没定，就要全量返工，代价最大。

### 步骤 1 · 生成资产骨架（AI，一次）

用 **P0** 一次性建出资产骨架与目录结构（`openspec/` 除外 —— 它由 CLI 生成，见步骤 4）。

- **产出**：`AGENTS.md`、`CONTEXT.md`、`.agents/project/`（4 篇）、`docs/adr/`、`hermes/`（3 库），以及**本项目实际使用的工具**所对应的指针文件。
- **验收**：`AGENTS.md` < 2000 字符（halo 实测 2058 可作参考上限）；`hermes` 下**没有任何经验条目**；所有索引路径真实存在；没有为本项目不使用的工具创建空壳入口。

### 步骤 2 · 填领域词汇（AI 起草 + 人工确认）

用 **P1** 让 AI 起草，你只做确认与修正。

- **产出**：`CONTEXT.md` 的边界词表，每条含「_避免_：」禁用词行。
- **验收**：每个词都能回答"它和最容易混的那个词差在哪"；标「需确认」的项都被你处理过。

### 步骤 3 · 定入口与知识库索引（AI）

用 **P2** 生成 `AGENTS.md` 六节正文与 `.agents/project/README.md` 的任务映射表。

- **验收**：`AGENTS.md` **只做索引，不复制内容**；映射表覆盖 `workflow.md` / `architecture.md` / `pitfalls.md` 三篇。
- **红线**：一旦 `AGENTS.md` 开始承载细节，它就会退化成第二本长文档并必然腐烂。

### 步骤 4 · 立规格骨架（CLI 一条命令，不是手写）

**这一步不该让 AI 手写 `config.yaml`** —— OpenSpec 自带 `init` 命令：

```bash
openspec init --tools <工具列表> --language <语言>
```

- `--tools` 接受逗号分隔的工具名，或 `all` / `none`。已支持的包括：`claude`、`cursor`、`codex`、`github-copilot`、`trae`、`codebuddy`、`gemini`、`qwen`、`kimi`、`kiro`、`windsurf`(devin)、`zed`、`agents` 等 40 余个。
- `--language` 决定新产物用什么语言书写。
- 该命令一次完成：建立 OpenSpec root、写入 `config.yaml`、**并为每个指定工具生成对应的斜杠命令与 skill 文件**。

证据：本仓库 `.trae/skills/openspec-*/SKILL.md` 的 frontmatter 带 `author: openspec` 与 `generatedBy: "1.10.0"` —— 这批文件是 `openspec init --tools trae` 的产物，不是手写的。这也是为什么它们能随 CLI 升级而更新（`openspec update`）。

- **要点**：项目背景写进 `config.yaml` 的 `context` 字段（会喂给 AI 生成产物）；**不要预建能力目录**，第一条变更来了自然会长出来。
- **验收**：`openspec context` 能正确解析出 root；目标工具的目录下出现 `openspec` 的技能文件。

### 步骤 5 · 写首条 ADR（人工 + AI）

用 **P4** 写"技术栈选型"这条 ADR。它同时完成两件事：记录第一个真实决策、把 ADR 模板用真实内容定型。

- **验收**：包含「备选方案与为何否决」与「触发重审条件」两节 —— 这两节是 ADR 的价值所在，缺了就只是流水账。

### 步骤 6 · 立门禁（AI，**不可省、不可延后**）

用 **P5** 生成 CI 配置、`commitlint` + `husky` + `lint-staged`、覆盖率阈值。

- **必须在本项目产生第二个提交之前完成。**
- **验收**：干净环境一次跑通；故意提交一个 lint 错误能被拦住；故意提交一个 `feat xxx` 能被 commitlint 拦下。
- **红线**：门禁一旦延后，就会面对"存量全红"，于是只能无限期搁置 —— 这是存量项目补不齐资产层的头号原因。

### 步骤 7 · 首个变更走完五阶段（AI 执行 + 人工在 3 处介入）

用 **P6.1 ~ P6.5** 依次走 explore → propose → apply → verify → archive。

- **人只在这三处介入**：规格评审（P6.2 产出后）、独立评审（P6.3 产出后）、回填确认（P6.5）。
- **验收**：产出一个归档变更 + 第一条 `hermes` 回填记录 + 第一条新增 ADR（如果这个变更做了不可逆决策）。

## 2. 提示词库

### P0 · 资产骨架一键生成

```text
你是本项目（<项目名>）的工程体系搭建助手。请按顺序创建 AI 工程化资产骨架。

项目信息：
- 项目名：<项目名>
- 一句话定位：<一句话业务定位>
- 技术栈：<技术栈>
- 主要目录：<主要目录结构>

请创建以下文件：
1. CONTEXT.md —— 领域词汇表，只建两张表骨架（业务域 / 技术词汇），内容留空待填
2. AGENTS.md —— 六节骨架：## 项目概况 / ## 关键目录 / ## 开发硬规则 / ## 需先问的变更 / ## 按需阅读 / ## 常用命令；每节 1 行占位，**总长不超过 2000 字符**
3. .agents/project/README.md —— 「任务 → 先读哪几篇」映射表骨架 + 文档边界说明
4. .agents/project/workflow.md —— 上下文读取策略 + 修改代码前检查清单 + 命令安全边界
5. .agents/project/architecture.md —— 目录结构与分层说明（先真实读取现有目录，不要虚构）
6. .agents/project/pitfalls.md —— 空表 + 维护约定（症状 → 根因 → 规避）
7. ~~openspec/config.yaml、specs/、changes/~~ —— **不要创建**，`openspec/` 由 CLI 生成，见 P3
8. docs/adr/README.md —— ADR 索引表骨架 + 命名约定 NNNN-kebab-title.md
9. hermes/README.md、hermes/pitfalls/README.md、hermes/decisions/README.md、hermes/patterns/README.md —— 只写「这库存什么 / 何时读 / 维护约定」
10. 多工具入口指针 —— **只为本项目实际使用的工具创建**（如用 Claude Code 才建 CLAUDE.md）。Codex / Kilo Code 原生读 AGENTS.md，不需要指针。不确定时先不建

> ⚠️ **本清单已被 [ADR 0017](adr/0017-constraint-docs-single-routing-table.md) 部分推翻（2026-09-21）**。照第 2、3 项施工会产生**已废弃的结构**：
>
> - **第 2 项**「六节骨架 + 总长 ≤2000 字符」：**字符上限已放弃**。本仓实际为 8 节 / 8264 字符；六节中的「## 需先问的变更」也未独立成节——需确认的变更收在「开发硬规则」的子列表里。节数以真实内容为准，不要为凑节数删内容。
> - **第 3 项**「创建 `.agents/project/README.md` 映射表」：**该文件已删除，不要再创建**。路由表只有一个家 = `AGENTS.md` 的「按需阅读与同步更新」（读方向 + 写方向同一张表）；语料目录持有索引会与它必然漂移（实测已漂出 3 条死链），且 `pnpm docs:check` 会把语料目录里的 `README.md` 直接判为违规。
> - **第 8 项** `docs/adr/README.md`：本仓**未创建**且暂不需要——ADR 索引的「结论版」在 `hermes/decisions/README.md`，「权威版」是 `docs/adr/` 目录本身。
>
> 其余各项（1、4、5、6、7、9、10）**仍然有效**。

硬约束：
- 不要把 AGENTS.md 的内容复制到其他文件
- 不要创建 openspec/ 下的任何文件（那是 CLI 的职责）
- 不要为本项目不使用的工具创建空壳入口文件
- hermes 下不要编造任何经验条目，保持为空
- AGENTS.md 里所有索引路径必须真实存在，写完自行核对
- 全部用中文，保留英文技术术语

完成后输出：文件清单 + 每个文件用途一句话 + 下一步该填什么。
```

### P1 · 领域词汇起草

```text
请协助起草 CONTEXT.md 的领域词汇表。

我提供的待定概念（原始输入，可能不准确）：
- <概念A> vs <概念B>：<我理解的区别>
- <概念C>：<团队日常叫法，可能不规范>
- <概念D>：<我拿不准它算不算独立概念>

要求：
1. 对每组概念输出：规范名称 / 精确定义 / 标识或登录方式 / 生命周期差异 / 易混淆项
2. 每条必须包含一行「_避免_：」，列出当前被误用的叫法
3. 只写真正容易混的词，不要为凑数添加显而易见的项
4. 不确定的标注「需确认」，不要猜

输出：可直接粘贴进 CONTEXT.md 的 Markdown 表格。
```

### P2 · 入口与知识库索引

```text
请基于以下信息生成 AGENTS.md 正文与 .agents/project/README.md。

项目信息：<项目名 / 技术栈 / 目录结构 / 一句话定位>
领域词汇（已完成）：<粘贴 CONTEXT.md 的核心边界词>

要求：
1. AGENTS.md 严格六节结构，总长不超过 2000 字符，只放硬规则与索引：
   - ## 项目概况：是什么 + 技术栈 + 架构形态（不超过 3 行）
   - ## 关键目录：每个目录一行，只写职责
   - ## 开发硬规则：本项目不可违反的约束，逐条短句（5~10 条）
   - ## 需先问的变更：哪些改动必须先确认
   - ## 按需阅读：任务 → 文档 的映射表
   - ## 常用命令：最常用的 5~8 条
2. .agents/project/README.md 写「任务 → 先读」映射表，并声明文档边界：
   AGENTS.md 自动加载只放索引 / .agents/project 是按需知识库 / docs 是产品文档
3. 硬规则要具体可执行（写"禁止返回未过滤的对象"，不要写"注意代码质量"）
4. 索引路径必须真实存在，写完逐个核对

输出：两个文件的完整内容 + 一份"我核对过的路径清单"。
```

### P3 · 规格骨架（先跑 CLI，再让 AI 填 context）

**不要用提示词让 AI 手建 `openspec/`。** 正确顺序是：先执行 CLI 命令建骨架，再让 AI 只负责填 `context` 字段。

**第一步（人执行 CLI）**：

```bash
openspec init --tools <本项目实际使用的工具,逗号分隔> --language zh
```

**第二步（把下面这段给 AI，只做填字段这一件事）**：

```text
`openspec init` 已经建好了 openspec/ 骨架。请只修改 openspec/config.yaml 的 context 字段，不要改动其他任何文件。

项目背景（填进 context 字段）：
- 技术栈：<技术栈>
- 架构分层：<分层说明>
- 领域边界（来自 CONTEXT.md）：<关键边界词>
- 提交规范：Conventional Commits，描述用中文
- 术语与语言约定：产物用中文，保留英文技术术语

要求：
1. 只改 context 字段，schema 保持 spec-driven 不动
2. context 会喂给 AI 生成产物，所以要写**具体约束**而非泛泛描述
   （反例："注意代码质量"；正例："对外只暴露业务 UUID，禁止暴露数据库自增 id"）
3. 暂时不写 rules 与 operations 字段（等有真实需要再加）
4. 不要预建任何能力目录 —— 第一条变更来了自然会长出来

输出：config.yaml 的 diff + 确认没有改动其他文件。
```

> **为什么必须走 CLI**：`init` 生成的不只是 `config.yaml`，还有各工具的斜杠命令与 skill 文件（可辨认标志是 frontmatter 里的 `author: openspec` 与 `generatedBy`）。手写会漏掉这些集成文件，而且无法通过 `openspec update` 随 CLI 升级。**凡是工具自带初始化命令的，永远不要用提示词模拟它。**

### P4 · 首条 ADR

```text
请写本项目的第 1 条 ADR：技术栈选型。

技术栈：<技术栈>
选择理由（我的原始表述）：<为什么选它>

格式（NNNN-kebab-title.md，四位编号）：
1. ## 背景 —— 当时的约束与问题
2. ## 决策 —— 选了什么，一句话结论
3. ## 备选方案与为何否决 —— 每个被否的方案写「为何否决 + 何时复活」
4. ## 后果 —— 得到的与付出的代价
5. ## 触发重审条件 —— 什么情况下该重新考虑这个决策

硬要求：
- 第 3 节和第 5 节不得留空，这两节是 ADR 的价值所在
- 写"为什么不选另一个"，不要只写"为什么不选错的那个"
- 不要美化决策，代价要如实写

同时更新 docs/adr/README.md 的索引表，加入这一条。
```

### P5 · 门禁配置

```text
请为本项目建立门禁配置（这是资产层唯一的强制装置，不可省）。

技术栈：<技术栈>
包管理器：<pnpm/npm/yarn>
测试框架：<jest/vitest>

请创建：
1. .github/workflows/ci.yml —— push 与 PR 触发，job 依次执行
   lint → typecheck → test → build，任一失败即整体失败
2. commitlint.config.js —— 采用 Conventional Commits，中文描述允许
3. husky 钩子：
   - pre-commit：lint-staged（只检查暂存文件）
   - commit-msg：commitlint
4. 覆盖率阈值：初始设 lines 30 / functions 30，写进测试配置并加注释「随项目提升」
5. package.json 补 prepare 脚本安装 husky

约束：
- 不要改动任何现有业务代码
- 所有配置必须能在干净环境一次跑通
- 给出本地验证命令，并给出"如何故意触发失败以确认门禁生效"的步骤

输出：每个文件的完整内容 + 本地验证步骤 + 说明每条门禁在失败时的提示信息。
```

### P6 · 单次变更五阶段

**P6.1 · 定案 explore**

```text
需求：<原始需求描述>

请进入定案模式，不要写任何代码。目标是把需求变成可落地的行为规格。

请输出：
1. 我对需求的理解（如果我理解错了请指出）
2. 需要澄清的问题 —— 只问会实质影响范围、外部可见行为、兼容性或验收标准的问题；次要细节自行假设并标注
3. 已定基线：本次变更明确要达成的行为口径，逐条写
4. Out of scope：本次不做、且不要顺手做的项，逐条写并说明为何排除
5. 禁止重开：哪些已决事项不得在本轮推翻
6. 涉及范围：哪些模块/文件会受影响

硬约束：本轮只产出上述内容，不要开始设计实现方案，不要改任何代码。
```

**P6.2 · 规格 propose**

```text
基于上一步的定案结论，请创建 OpenSpec 变更并生成全部规划产物。

变更名（kebab-case）：<change-name>

请生成并在写完后逐个核对存在性：
1. proposal.md —— 为什么做（背景、问题、目标、非目标）
2. specs/<capability>/spec.md —— 这个能力的 delta（相对现有规格的增删改），不是完整规格
3. design.md —— 怎么做（方案、权衡、被否决的方案）
4. tasks.md —— 可勾选的实现步骤，每步具体到文件

硬约束：
- 本阶段是 planning boundary：绝对不要改业务代码，即使我在这条消息里说了"顺便实现"
- tasks 要拆到"每一步都能独立验证"，不要写"实现 XX 模块"这种粗粒度
- 写完后停下来等我评审规格，不要自行进入实现

输出：产物清单 + 我需要在评审时重点看什么。
```

**P6.3 · 实现 apply**

```text
请按 tasks.md 逐条实现这个变更。

要求：
1. 开工前先读全部规划产物（proposal / specs / design / tasks），从磁盘重读
2. 对每条任务：先说明要做什么 → 实现 → 立即在 tasks.md 把 `- [ ]` 改成 `- [x]`
3. 测试先行：能写测试的步骤先写测试（红）再实现（绿）
4. 保持改动最小且聚焦，不顺手重构无关代码

必须暂停并上报的情况：
- 任务描述不清 → 先问
- 实现中发现设计问题 → 停下来说明并建议改规划产物
- 任务需要超出规格描述的范围，或你产生了"缩小范围/推迟/接受例外"的念头 → 必须把新增范围讲清楚并等我决定，绝不静默处理

硬约束：只有在该任务的行为被完整实现后才允许打勾；部分完成或推迟的不许打勾。

输出：每条任务的实现说明 + 完成后的进度 N/M + 我该重点评审哪些改动。
```

**P6.4 · 验证 verify**

```text
请验证本次实现与规划产物是否一致，不要修改代码。

请输出：
1. 逐条比对 specs 里的每个行为要求 → 实现是否满足，给出证据（文件:行）
2. 逐条检查 tasks.md 是否有未完成却被打勾的项
3. 检查是否有超出规格范围的改动混入
4. 运行全量测试与类型检查，贴出结果（不接受只跑相关用例）
5. 如果接口有变化，给出契约 diff
6. 明确列出"未验证项"与"无法验证项"，不要用推断代替验证

硬约束：不要为了让验证通过而修改代码；发现问题只报告，等我来定处理方式。
```

**P6.5 · 归档与回填**

```text
本次变更已完成验证。请执行收尾，分三步并逐步确认：

第一步 · 归档
1. 把 delta specs 合回 openspec/specs/ 的对应能力主规格
2. 把变更移入 openspec/changes/archive/YYYY-MM-DD-<change-name>/

第二步 · 回填经验（这一步最容易漏，请务必执行）
3. 本次是否踩了坑？有则追加到 hermes/pitfalls/，格式：症状 → 根因 → 规避 + 源码链接
4. 是否形成了可复用的工程模式？有则追加到 hermes/patterns/
5. 是否做了不可逆决策？有则新增 ADR，并更新 hermes/decisions/ 的 ADR 索引表
6. 回填时先搜索是否已有同类条目，有则合并，不要开第二个入口

第三步 · 同步资产
7. 本次是否引入了新术语？有则更新 CONTEXT.md
8. 本次是否改变了某条硬规则？有则更新 AGENTS.md（注意只改索引与规则，不要把细节搬进去）
9. 本次是否新增/删除了主题文档？有则同步 .agents/project/README.md 的映射表

输出：三步各自的完成清单 + 明确指出哪些步骤本次无需执行及原因。
```

### 3.6 多工具入口：谁需要指针，谁不需要

**先说清命名**：`AGENTS.md` 是开放标准（由 Agentic AI Foundation / Linux Foundation 托管，6 万+ 项目采用，出自 OpenAI Codex、Amp、Google Jules、Cursor、Factory 的协作）。`.agents/` 是**该标准中的工具配置目录约定**（存放 skills / memories / subagents 等，并可用 `.agents/AGENTS.md` 作为项目基础规则层）。

> **不要自造 `.ai/`**。`.ai/` 不是跨厂商标准，只是个别项目（如 Adobe spectrum-web-components）自选的目录名。它的做法值得借鉴（工具无关目录 + 各工具薄适配器），但**目录名请用有标准可依的 `.agents/`**。

各工具实际读哪个文件（决定了谁需要指针）：

| 工具 | 规则文件 | 是否需要指针 |
| --- | --- | --- |
| OpenAI Codex / Kilo Code | `AGENTS.md` | **不需要**（原生读取） |
| Claude Code | `CLAUDE.md` | **需要** |
| GitHub Copilot | `.github/copilot-instructions.md` | **需要** |
| Cursor | `.cursorrules`（或 `.cursor/rules`） | **需要** |
| Windsurf / Devin | `.windsurfrules` | **需要** |
| Gemini | `GEMINI.md` | **需要** |

**两种指针写法，按工具选**：

1. **导入指令**（Claude Code 的写法，推荐）：

```markdown
@AGENTS.md

# 以下为 Claude Code 专属覆盖规则（仅当确有差异时才写）
```

2. **软链**（工具不支持下述语法时）：

```bash
ln -s AGENTS.md CLAUDE.md
ln -s AGENTS.md .cursorrules
```

> 单一真源在 `AGENTS.md`，其余文件只做指针。**不要复制内容** —— 复制即产生第二份会腐烂的副本。
> 若团队只用 Codex 一类原生读 `AGENTS.md` 的工具，则**一个指针文件都不需要建**，不要为了"看起来完整"而制造空壳。

| 不要做 | 为什么 |

## 6. 棕地增量开发：流程如何复用

存量项目上做增量开发时，本手册**后半段可原样复用，前半段必须变形**。

### 6.1 复用结论

| 步骤 | 棕地处置 |
| --- | --- |
| 0 准备输入 | **替换** —— 先划 AI 可写范围，再盘点存量 |
| 1 生成资产骨架 | **替换** —— 从现有代码逆向提取，不凭想象 |
| 2 填领域词汇 | **替换** —— 从代码与 schema 反推边界词 |
| 3 定入口与知识库索引 | **原样复用**（路径须指向真实位置） |
| 4 立规格骨架 | **原样复用**（增量：存量不回填） |
| 5 写首条 ADR | **替换** —— 回溯补"最易被推翻"的历史决策 |
| 6 立门禁 | **改策略** —— 棘轮：只允许收紧不放松 |
| 7 变更五阶段 | **原样复用** —— 这就是增量开发本身 |
| —— | **新增** —— 存量共识回溯（近 3~6 月故障 → hermes） |

**核心原则反转**：绿地是"先定词汇再写代码"，棕地是"先读代码再提取词汇"。

> **棕地的一切资产都必须从既有代码与 schema 提取，不能凭空生成。** AI 照着一份与实际代码不符的词汇表去理解项目，比没有词汇表更糟 —— 它会带着错误的确定性工作。

### 6.2 门禁的棘轮策略（最关键的一步）

绿地 CI 从第一天全绿；棕地一开跑不过。**如果一开始就要求全量通过，等于永远不开门禁。**

| 维度 | 棕地启动策略 | 收紧方式 |
| --- | --- | --- |
| lint | 只对暂存 / 改动文件强制（lint-staged） | 逐步扩到全量；新规则禁止增量违反 |
| typecheck | 项目类型本已严则全量开 | 否则先只查改动文件 |
| test | 先只跑"受影响模块" | 逐步扩到全量；新代码必须有测试 |
| 覆盖率 | **阈值 = 当前实测值**（如 42%） | **棘轮：只升不降**，下降即阻断 |
| 安全扫描 | 先只报告不阻断 | 收敛后改为阻断 |

**棘轮（ratchet）是棕地防腐的核心手法：门禁只能收紧，不能放松。** 每有人提升覆盖率，阈值随之上抬且不再回落 —— 存量会在无人专门治理的情况下被动收敛。

### 6.3 AI 可写范围（棕地独有，必做）

绿地不存在这个问题，棕地必须显式划定，否则 AI 的改动会落在最不该碰的地方。做法：

1. **禁区**：涉及资金、权限、鉴权、数据迁移的核心路径，以及无人维护的遗留模块
2. **可写区**：本次增量涉及的模块
3. **写进 `AGENTS.md` 的硬规则**（这是硬规则里优先级最高的一类）

### 6.4 存量不回填，只写增量

不要试图给全仓补规格 —— 不可能，也不值。正确做法是**变更驱动补规格**：

- 本次增量涉及的模块 → 写 spec delta（OpenSpec 的 delta 机制天然适配）
- 未涉及的存量 → 完全不动
- **需要修改存量代码时 → 先补该模块的"现状规格"再改**（这本身应作为一次变更走流程）

### 6.5 棕地的红利：经验库可以立刻有内容

绿地的 `hermes` 第一天必须为空；棕地相反 —— 团队已经踩过坑，**第一天就能有真东西**。

做法：回溯最近 3~6 个月的线上故障与返工，只写「症状 → 根因 → 规避」，一条不编。

同理 ADR：不做全量考古，只补**最容易被推翻**的历史决策（被推翻风险 × 出现频率最高的那几条）—— 因为 ADR 的全部价值就是"别再推翻"。

### 6.6 可复用的提示词

`P6.1 ~ P6.5`（单次变更五阶段）与 `P7.1 ~ P7.4`（维护类）**原样复用**。

需要替换的是 `P0` / `P1` / `P4` —— 把"生成 / 起草"改成"提取 / 反推"：

#### P0' · 棕地资产逆向提取

```text
你是本项目的工程体系改造助手。本项目已有大量存量代码，请**逆向提取** AI 工程化资产，不要凭空生成。

第一步 · 只读盘点（先不要写任何文件）
1. 真实读取目录结构，输出分层与模块职责
2. 读取数据模型定义（schema.prisma / migration / ORM model），提取实体与关系
3. 读取现有 README / docs / 关键注释，提取团队已形成的约定
4. 读取最近 50 条提交，提取实际的提交规范与命名习惯

第二步 · 提取输出（等我确认后再落盘）
1. 候选领域概念清单，每条标注「依据：文件:行」
2. 最易混的 3~5 对概念及其区分点
3. 目录职责表
4. 现有但未成文的硬规则候选（从代码惯例反推）
5. 本次增量可能触及的模块清单

硬约束：
- 每条结论必须给出来源（文件:行 或 commit hash），无依据的标注「推测」
- 本步骤不要修改任何文件，只输出盘点结果
- 不要用通用最佳实践替代本项目的实际做法
```

#### P1' · 棕地领域词汇反推

```text
请基于上一步的代码盘点结果，反推 CONTEXT.md 的领域词汇表，不要问我也不要凭空编。

要求：
1. 从数据模型、枚举、状态字段、命名冲突中提取真正的领域概念
2. 重点识别**看起来相似但实际不同**的概念对（例如两张不同的表 / 两个不同的字段指向同一个业务词）
3. 每条必须给出「依据：文件:行」
4. 存疑项标注「存疑」，我在确认环节处理
5. 每条带「_避免_：」行，列出代码或注释中出现过的其他叫法

输出：可直接粘贴进 CONTEXT.md 的表格 + 一份「我拿不准，需要你确认」的清单。
```

#### P4' · 历史决策回溯补 ADR

```text

输入：

- 我印象中团队反复争论 / 反复改动过的地方：<列举>

只挑 3~5 条同时满足以下条件的决策写 ADR：
1. 不可逆，或改起来代价很大
2. 团队至今仍在争论，或被推翻过不止一次
3. 本次增量可能会触及
```

### 6.7 反面清单补充（棕地专属）

| 不要做 | 为什么 |
| --- | --- |
| 让 AI 凭空生成领域词汇表 | 与实际代码不符的词汇表比没有更糟 —— AI 会照它理解项目 |
| 一上来要求 CI 全量通过 | 存量必红，结果就是永远不开门禁 |
| 试图给全仓补规格 | 不可能也不值。只补增量涉及的模块 |
| 改存量行为却不先补现状规格 | 没有现状规格就无法验证改动是否正确 |
| 全量考古补 ADR | 只补"最易被推翻"的几条，其余留给真实决策时 |
| 让 AI 自由选择改动位置 | 棕地必须先划禁区与可写区 |
| 保留过期的本地索引 / 架构图 | 描述旧架构的图比没有更危险。**先删再按需重建** |
