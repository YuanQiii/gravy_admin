## 1. 总览：三种频率的循环

AI 工程化不是一条直线，而是**三个频率差一个数量级的循环**：

| 循环 | 频率 | 触发点 | 时长 |
| --- | --- | --- | --- |
| **初始化** | 一次性 | 项目启动 / 引入 AI 工程化 | 半天 |
| **迭代** | 每次变更 | 一个需求 / 一个 PR | 数小时 |
| **维护** | 周期性 | 每周、每版本、每次合并前 | 10~30 分钟 |

**为什么要分开看**：三种频率混在一起，低频的必然被高频的挤掉——这就是"文档总说有空再更新结果永远没更新"的机制原因。**必须把每个循环挂在一个已经发生的动作上，而不是挂在提醒上。**

## 2. Part A · 初始化（一次性）

### A.0 前置：准备三样输入（人工，约 10 分钟）

先想清楚并写下来，作为后面所有步骤的输入：

1. **技术栈与目录结构** —— 已确定的，不要边建边改
2. **一句话业务定位** —— 用于 `AGENTS.md` 的「项目概况」
3. **3~5 个最容易混的领域概念** —— 这是 `CONTEXT.md` 的唯一输入，也是最容易被跳过的一步

> **提示词**（可选，帮你把易混概念想全）：
>
> ```text
> 我要为本项目起草领域词汇表。请帮我列出「最容易在团队内被混用」的概念候选，覆盖以下角度：
> 1. 两个相似但生命周期不同的业务实体（例如买家 vs 后台操作者）
> 2. 一个被日常口语滥用、实际有精确含义的词
> 3. 同一业务词在代码里对应了多个不同对象的情况
> 每个候选只需给出：概念名 + 为什么容易混 + 我的确认问题。
> 不要给出定义，我要自己确认。
> ```
>
> **为什么这步不能省**：领域词汇是后面所有文档的用词基准。等写完一堆文档才发现术语没定，就要全量返工——这是八步里唯一"顺序错了代价最大"的一步。

### A.1 生成资产骨架（AI，一次）

用 playbook 的 **P0** 一次性建出除 `openspec/` 外的全部骨架。

- **产出**：`AGENTS.md`、`CONTEXT.md`、`.agents/project/`（4 篇）、`docs/adr/`、`hermes/`（3 库）、本项目实际使用工具的指针文件
- **验收**：`AGENTS.md` < 2000 字符；`hermes` 下**没有任何经验条目**；所有索引路径真实存在

### A.2 填领域词汇（AI 起草 + 人工确认）

用 playbook 的 **P1**。

- **产出**：`CONTEXT.md` 边界词表，每条含「_避免_：」禁用词行
- **验收**：每个词都能回答"它与最容易混的那个词差在哪"；标「需确认」的项都已处理

### A.3 定入口与知识库索引（AI）

用 playbook 的 **P2**。**这一节最关键的是长度控制**：`AGENTS.md` 必须保持薄入口。

- **验收**：只做索引不复制内容；六节结构完整（项目概况 / 关键目录 / 硬规则 / 需先问的变更 / 按需阅读 / 常用命令）
- **红线**：一旦它开始承载细节，就会退化成第二本长文档并必然腐烂

### A.4 立规格骨架（**CLI，不是手写**）

```bash
openspec init --tools <本项目实际使用的工具,逗号分隔> --language zh
```

**不要用提示词让 AI 手建 `openspec/`** —— 手写会漏掉各工具的斜杠命令与 skill 文件，且无法通过 `openspec update` 随 CLI 升级。

建好后，用 playbook 的 **P3** 让 AI **只填 `config.yaml` 的 `context` 与 `rules` 字段**（这两个字段会喂给所有 OpenSpec 产物，务必写具体约束）。

- **验收**：`openspec context` 能正确解析出 root
- **注意**：`rules` 要写**可执行的原子约束**，例如「Backend changes must pass `spotlessCheck`」，而不是「注意代码质量」

### A.5 写首条 ADR（人工 + AI）

用 playbook 的 **P4**。第 1 条建议就写"技术栈选型"，顺便用真实内容把模板定型。

- **验收**：包含「**备选方案与为何否决**」与「**触发重审条件**」两节——这两节是 ADR 的全部价值，缺了就只是流水账

### A.6 立门禁（AI，**不可省、不可延后**）

用 playbook 的 **P5**。

- **必须在本项目产生第二个提交之前完成**
- **验收**：干净环境一次跑通；**故意触发一次失败，确认能被拦住**
- **棕地例外**：存量项目改用**棘轮**（阈值 = 当前实测值，只升不降），见 §5.2

### A.7 初始化总验收清单

```
[ ] AGENTS.md 字符数 < 2000，且六节结构完整
[ ] AGENTS.md 中所有索引路径真实存在（grep 逐条核对）
[ ] CONTEXT.md 的每个边界词都有「_避免_：」行
[ ] openspec init 已执行，config.yaml 的 context 与 rules 已填实
[ ] docs/adr/ 有第 1 条 ADR，且含「为何否决」与「重审条件」
[ ] hermes/ 三库的 README 已写维护约定，且内容为空
[ ] CI 能在干净环境跑通，且故意触发失败能被拦住
[ ] 未为本项目不使用的工具创建空壳入口文件
```

## 3. Part B · 迭代（每次变更）

### 3.1 五阶段与人机分工

**五个阶段里只有两个由 AI 独立完成，三个需要人介入。** 人的介入点集中在"判断"上，AI 负责"执行"与"枚举"。

| 阶段 | 主导 | 人的动作 |
| --- | --- | --- |
| ① 定案 explore | AI | — |
| ② 规格 propose | AI 产出 | **规格评审**（最高性价比的人工介入） |
| ③ 实现 apply | AI | **独立评审**（AI 不能自证） |
| ④ 验证 verify | AI | — |
| ⑤ 沉淀 archive | AI | **回填确认** |

> **为什么规格评审最值钱**：改规格比改代码便宜一个数量级。在 ② 拦下一个错误需求，成本是 ③ 的十分之一。

### 3.2 各阶段的提示词

**B.1 · 定案 explore**（playbook `P6.1`）

```text
需求：<原始需求描述>

请进入定案模式，不要写任何代码。目标是把需求变成可落地的行为规格。

请输出：
1. 我对需求的理解（如果我理解错了请指出）
2. 需要澄清的问题 —— 只问会实质影响范围、外部可见行为、兼容性或验收标准的问题；次要细节自行假设并标注
3. 已定基线：本次变更明确要达成的行为口径，逐条写
4. Out of scope：本次不做、且不要顺手做的项，逐条写并说明为何排除
5. 禁止重开：哪些已决事项不得在本轮推翻
6. 涉及范围：哪些模块/文件会受影响

硬约束：本轮只产出上述内容，不要开始设计实现方案，不要改任何代码。
```

**B.2 · 规格 propose**（playbook `P6.2`）← **人介入点 1**

```text
基于上一步的定案结论，请创建 OpenSpec 变更并生成全部规划产物。

变更名（kebab-case）：<change-name>

请生成并在写完后逐个核对存在性：
1. proposal.md —— 为什么做（背景、问题、目标、非目标）
2. specs/<capability>/spec.md —— 这个能力的 delta（相对现有规格的增删改），不是完整规格
3. design.md —— 怎么做（方案、权衡、被否决的方案）
4. tasks.md —— 可勾选的实现步骤，每步具体到文件

硬约束：
- 本阶段是 planning boundary：绝对不要改业务代码，即使我在这条消息里说了"顺便实现"
- tasks 要拆到"每一步都能独立验证"，不要写"实现 XX 模块"这种粗粒度
- 写完后停下来等我评审规格，不要自行进入实现

输出：产物清单 + 我需要在评审时重点看什么。
```

**B.3 · 实现 apply**（playbook `P6.3`）← **人介入点 2**

```text
请按 tasks.md 逐条实现这个变更。

要求：
1. 开工前先读全部规划产物（proposal / specs / design / tasks），从磁盘重读
2. 对每条任务：先说明要做什么 → 实现 → 立即在 tasks.md 把 `- [ ]` 改成 `- [x]`
3. 测试先行：能写测试的步骤先写测试（红）再实现（绿）
4. 保持改动最小且聚焦，不顺手重构无关代码

必须暂停并上报的情况：
- 任务描述不清 → 先问
- 实现中发现设计问题 → 停下来说明并建议改规划产物
- 任务需要超出规格描述的范围，或你产生了"缩小范围/推迟/接受例外"的念头
  → 必须把新增范围讲清楚并等我决定，绝不静默处理

硬约束：只有在该任务的行为被完整实现后才允许打勾；部分完成或推迟的不许打勾。

输出：每条任务的实现说明 + 完成后的进度 N/M + 我该重点评审哪些改动。
```

**B.4 · 验证 verify**（playbook `P6.4`）

```text
请验证本次实现与规划产物是否一致，不要修改代码。

请输出：
1. 逐条比对 specs 里的每个行为要求 → 实现是否满足，给出证据（文件:行）
2. 逐条检查 tasks.md 是否有未完成却被打勾的项
3. 检查是否有超出规格范围的改动混入
4. 运行全量测试与类型检查，贴出结果（不接受只跑相关用例）
5. 如果接口有变化，给出契约 diff
6. 明确列出"未验证项"与"无法验证项"，不要用推断代替验证

硬约束：不要为了让验证通过而修改代码；发现问题只报告，等我来定处理方式。
```

**B.5 · 沉淀 archive**（playbook `P6.5`）← **人介入点 3**

```text
本次变更已完成验证。请执行收尾，分三步并逐步确认：

第一步 · 归档
1. 把 delta specs 合回 openspec/specs/ 的对应能力主规格
2. 把变更移入 openspec/changes/archive/YYYY-MM-DD-<change-name>/

第二步 · 回填经验（最容易漏，务必执行）
3. 本次是否踩了坑？有则追加到 hermes/pitfalls/，格式：症状 → 根因 → 规避 + 源码链接
4. 是否形成了可复用的工程模式？有则追加到 hermes/patterns/
5. 是否做了不可逆决策？有则新增 ADR，并更新 hermes/decisions/ 的 ADR 索引表
6. 回填前先搜索是否已有同类条目，有则合并，不要开第二个入口

第三步 · 同步资产
7. 本次是否引入新术语？有则更新 CONTEXT.md
8. 是否改变了某条硬规则？有则更新 AGENTS.md（只改索引与规则，不要把细节搬进去）
9. 是否新增/删除了主题文档？有则同步 .agents/project/README.md 的映射表

输出：三步各自的完成清单 + 明确指出哪些步骤本次无需执行及原因。
```

## 4. Part C · 维护（周期性）

四个检查，**各自挂在一个已经发生的动作上**：

| 检查 | 挂在什么动作上 | 提示词 |
| --- | --- | --- |
| 回填经验 | 变更归档后（= B.5 第二步） | `P7.1` |
| 索引同步 | 每次合并前 / 每周 | `P7.2` |
| 防腐体检 | 每版本 / 每月 | `P7.3` |
| 新增主题文档 | 需要时 | `P7.4` |

四个提示词全文见 playbook §4。其中**最该定期跑的是 `P7.3` 防腐体检**（死链、路径漂移、索引新鲜度、空壳冗余、更新遗漏）——它专门用来发现"体系在悄悄腐烂"。

## 5. 两类项目的差异

### 5.1 绿地（新项目）

按 §2 的顺序执行即可。**关键：A.6 门禁必须在第二个提交之前。**

### 5.2 棕地（存量项目）—— 两个关键调整

**调整一：顺序反转。** 绿地是"先定词汇再写代码"，棕地是"**先读代码再提取词汇**"。所有资产必须从既有代码与 schema **逆向提取**，不能凭空生成——AI 照着一份与实际不符的词汇表理解项目，比没有词汇表更糟。

提示词改用 playbook 的 **`P0'`（资产逆向提取）/ `P1'`（词汇反推）/ `P4'`（历史决策回溯）**，共同点是把"生成/起草"改为"提取/反推"，且每条结论必须给出「依据：文件:行」。

**调整二：门禁改用棘轮（ratchet）。**

绿地 CI 从第一天全绿；棕地一开跑不过。**如果一开始就要求全量通过，等于永远不开门禁。**

| 维度 | 棕地启动策略 | 收紧方式 |
| --- | --- | --- |
| lint | 只对暂存 / 改动文件强制 | 逐步扩到全量；新规则禁止增量违反 |
| typecheck | 项目类型本已严则全量开 | 否则先只查改动文件 |
| test | 先只跑"受影响模块" | 逐步扩到全量；新代码必须有测试 |
| 覆盖率 | **阈值 = 当前实测值** | **棘轮：只升不降**，下降即阻断 |
| 安全扫描 | 先只报告不阻断 | 收敛后改为阻断 |

**棘轮是棕地防腐的核心手法：门禁只能收紧，不能放松。** 每有人提升覆盖率，阈值随之上抬且不再回落——存量会在无人专门治理的情况下被动收敛。

**棕地独有、必做的一项**：划定 **AI 可写范围与禁区**（资金、权限、鉴权、数据迁移的核心路径，以及无人维护的遗留模块），写进 `AGENTS.md` 硬规则。绿地不存在这个问题。

**棕地的红利**：`hermes` 第一天就能有真东西——回溯最近 3~6 个月的故障与返工，写成「症状 → 根因 → 规避」。

### 5.3 执行顺序（棕地建议四批）

按「失败成本 × 可独立验证」排，不按"重要性"排：

| 批次 | 内容 | 为什么在这个位置 |
| --- | --- | --- |
| 1 | 只改错（修正错误假设、死链、失效路径） | 正在持续损失，且纯文本可逆 |
| 2 | 量基线（覆盖率实测、lint 违规数） | 没有基线就设不出可执行阈值；只读零风险 |
| 3 | 建门禁，**阈值 = 基线** | 这样 CI 第一天就是绿的，它才活得下来 |
| 4 | 把已有资产接上门禁（文档校验、生成物漂移检测） | 先让门禁存在、基线明确，再接校验才有意义 |

**每一批必须能独立上线、独立验证、独立回滚。** 不设计"必须四批一起做完才有用"的方案——资产层最常见的死法不是做错，是做了一半没人用。

## 6. 常见失败模式与处置

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| `AGENTS.md` 越写越长 | 把它当知识库而非入口 | 用「删除测试」逐段裁剪；下沉到 `.agents/` 只留索引 |
| 文档路径指向不存在的文件 | 没有校验机制，重构后无人发现 | 把死链/路径校验放进 CI |
| 同一主题两处维护、逐渐不一致 | 靠"声明唯一事实源"而非机制 | 用软链 / `@AGENTS.md` 导入 / 生成命令，让副本物理上不可能独立存在 |
| 门禁建了又被绕过 | 只有本地钩子，没有服务端强制 | 加 CI；`--no-verify` 不能绕过服务端 |
| 门禁一开就红，于是被关掉 | 绿地策略用在棕地 | 改用棘轮：阈值 = 当前实测值 |
| 经验库空着没人写 | 回填靠自觉 | 把回填写进归档 checklist，做成流程的副产品 |
| AI 反复推翻已决事项 | 决策没有留痕 | 写 ADR，含「否决项 + 何时复活」 |
| AI 越界改动不该碰的地方 | 没有显式禁区 | 在 `AGENTS.md` 写「需先问的变更」清单 |
| 本地索引/架构图误导 AI | 过期生成物未清理 | **过期即删，不要修**——过期索引比没有索引更危险 |
| 体系建好但没人用 | 一次做完才交付，期间无收益 | 拆成能独立上线的小批次，每批都要有立刻可感知的收益 |

## 7. 一句话回到底层

整套流程只在做一件事：**让"该怎么做"变成"不做会失败"。**

规范写进文档只是建议，接上门禁才是约束；经验写在纸上只是记录，挂上归档动作才会回填；决策记在 ADR 里只是存档，被 AI 读到才会停止重开。

**AI 最大的风险从来不是"不知道"，而是"知道了但没被拦住"。**
