## 对照研究：unibest 与 GVRAY（产出 `docs/ai-engineering-comparison-unibest.md`）

以 GitHub API 拉取 `feige996/unibest` 的 `base` 分支（818 文件）完整树 + 8 个关键文件全文，与本项目逐项对照。

**unibest 的体系**：`AGENTS.md`（1.7KB 薄入口）+ `hermes/`（工程规范事实源，7 篇：architecture/conventions/platforms/api/sop-new-page/performance/release）+ `.agents/skills/`（16 个 skill + 按需导入速查表 + 导入规则 4 条）+ `.cursor/rules/*.mdc` ×3 + `.husky/`。

**unibest 值得借鉴**：① 门禁真建了 —— husky + @commitlint/cli + config-conventional + lint-staged + @changesets/cli + vitest + vue-tsc，且 `AGENTS.md` 把合入门禁写成可执行命令 `pnpm type-check && pnpm lint && pnpm test:run`；另有 `preinstall: npx only-allow pnpm` 锁包管理器。② `.agents/README.md` 是可执行的「任务场景 → skill → 路径」检索表 + 4 条导入规则 + 「区分易混淆项」。③ `openapi-ts-request` 从 OpenAPI 生成请求代码（契约驱动），GVRAY 只有 Swagger 文档无生成。

**GVRAY 独有且 unibest 完全没有**：openspec 规格驱动（10 主规格 + 20 归档）、docs/adr（14 条）、hermes 经验三库。

**核心发现 1 —— `hermes/` 同名异用（三义）**：unibest 的 `hermes/` = 工程规范事实源；GVRAY 的 `hermes/` = 经验教训库。两边 README 的命名理由几乎逐字一致（都援引"信使之神/信使"，都是"给开发者和 AI 传递"）→ 判断为**同一约定来源被各自继承，但语义各走各路**。第三个含义：`openspec init --tools` 里的 `hermes` 指 Hermes Agent（Nous Research，2026-02 发布，约 35k stars；其上下文文件优先级 `.hermes.md` → `AGENTS.override.md` → `AGENTS.md` → `CLAUDE.md` → `.cursorrules`），与项目内的 `hermes/` 目录无关。**建议：保留名字但在 CONTEXT.md 写明本地含义；合并时二选一或改名。**

**核心发现 2 —— 两边共犯的同一类错误（最重要）**：
- **都缺 CI**：unibest 有完整 husky 钩子但无可 `.github/`，`--no-verify` 即可绕过，且无合并前全量校验；GVRAY 连钩子都没有。**两边的"门禁"都只是本地约定，无服务端强制。**
- **都声明"唯一事实源"却并存已漂移的副本**：unibest `AGENTS.md` 写"详细规范唯一事实源在 hermes/"，但 `.cursor/rules/api-http-patterns.mdc` 独立复述且泛化（"可以用简单 http 或 alova 或 vue-query"三选一 vs hermes/api.md 的"错误四分类 / 401 双 token"）；`development-workflow.mdc` 内容为通用填充（"推荐 VSCode""console.log 调试"）且 frontmatter 错放在文件末尾。GVRAY 则是三对同名文档双写 + 3 死链 + 9 处旧路径。**病根：事实源是靠"声明"维持的，不是靠机制；只要存在第二份副本就必然漂移。**

**结论**：两者互补而非竞争（unibest = 规范传递型，GVRAY = 过程留痕型），但都在"保证 AI 不偏离"这一侧投入不足。**AI 最大的风险不是"不知道"，而是"知道了但没被拦住"。** 目标结构建议见文档 §6（入口取 unibest 的薄、规范源取 unibest 的场景切分、经验库取 GVRAY 三库、门禁取 unibest 并补 CI）。

## 术语澄清：规范事实源（实测结论）

**定义**：规范**唯一被编辑**的地方；其他一切出现都是它的**投影**（只读、不可独立编辑）。三属性：可编辑性（只它被直接改）、派生性（别处都是派生）、**物理唯一**（不是声明唯一）。

**两种真实策略**：
- **文档型**：事实源 = 一份文档（unibest 的 `hermes/`，其 AGENTS.md 明写"详细规范唯一事实源在 hermes/"）。优：可读可评审；险：会与代码脱节、易长副本。
- **代码型**：事实源 = 源码本身。**GVRAY 属于这一类** —— 实测 `grep -rn "事实源"` 在项目文档中 **0 命中**（仅命中本 memory 文件），但 `.agents/project/README.md` 的「文档边界」里有等价声明：「更新时以**源码/Swagger/OpenAPI** 为准，避免维护易过期清单」；`AGENTS.md` 硬规则亦有「文档与源码冲突时以源码为准」。**即 GVRAY 已隐式声明源码为事实源，只是没用"事实源"这个词。**

**三对同名文档实测体量（字符）**：
| 名称 | docs/ | .agents/project/ | 关系判断 |
| --- | --- | --- | --- |
| deployment | 3518 | 3153 | **同级双写（最危险，无"谁是源"的答案）** |
| configs | 4175 | 1051 | 详版 ↔ 摘要 |
| response-format | 2606 | 1007 | 详版 ↔ 摘要 |

**"唯一事实源"的四种形态**（前三种都会失败）：① 声明式（写"唯一在 X"但别处仍有完整副本）② 摘要式（副本是"摘要"但独立演化，更隐蔽）③ 流程式（靠"记得同步"，必然遗漏）④ **物理式（软链/`@` 导入/生成命令/CI `git diff --exit-code`）—— 唯一有效**。

**顺带发现的骨架不一致**：`openspec/specs/` 下 4/10 主规格多一个 H1（`# xxx Specification`），而 openspec 官方模板（`@fission-ai/openspec/schemas/spec-driven/templates/spec.md`）以 `## Purpose` 开头、无 H1。其余骨架合规度极高：10/10 用 `## Requirements`，归档变更是 15 处 `## ADDED Requirements` + 9 处 `## MODIFIED Requirements`，**163/163 个 Scenario 全部使用 `**WHEN**` 结构化写法**，正文用 RFC 2119 的 `SHALL` 措辞。
