架构深化评审

评审对象：openspec/changes/add-equipment-inquiry-customer-domains/design.md

时机：代码落地前——这是深化最便宜的时机。修正一个 shallow module 设计，比重构已落地代码便宜一个数量级。

基线观察

现有 BaseService（src/shared/services/base.service.ts）
  • • 9 个 protected 方法，其中 4 个 paginate 变种（paginate / paginateWithResponse / paginateWithSort / paginateWithSortAndResponse）是 (是否排序?) × (是否包装响应?) 的排列
  • • 每个变种实现极薄——paginateWithSortAndResponse 只是 paginateWithSort + ResponseUtil.paginated 的两行包装
  • • deletion test：删掉 3 个变种，复杂度几乎不回归到调用方 → shallow
现有软删除模式（permissions.service.ts:L34, L92）
  • • where['deletedAt'] = null 在每个 service 内联手写
  • • 唯一性 + 软删除冲突处理：design.md D4 计划在 9 个新 service 里复制 findFirst({ where: { name, deletedAt: null } }) 校验 + *_DUPLICATED_SOFT_DELETED 错误码
  • • 现有 22 个 model 中只有 Permission 有软删除，问题尚未显化；新设计会让它扩散到 9 处

词汇：用 module/interface/depth/seam/adapter/leverage/locality 描述。ADR-0001（MySQL→PG）与本评审无冲突；ADR-0002（独立 Customer）尚未创建，本评审不重新质疑该决策。

候选 1：软删除 + 唯一性校验集中化

Strong

Files

影响 design.md 的 9 个新 service：brands / catalogs / filter-types / filters / equipment / inquiries / inquiry-lines / customers / addresses。现状：permissions.service.ts 已内联一份。

Problem

design.md D4 明确要求"创建/恢复前用 findFirst 校验未软删除记录无同名"+"冲突返回 *_DUPLICATED_SOFT_DELETED"。这段逻辑会在 9 个 service 里逐字复制。deletion test：从任一 service 删掉它，复杂度原地留下——但复制 9 份意味着 bug 修一处漏八处，locality 丧失。

Solution

在 src/shared/services/ 新增一个深 module——SoftDeleteService（或 mixin），interface 仅 3 个方法：assertUniqueActive(model, field, value, excludeId?) / softDelete(model, id) / restore(model, id)。把 D4 的校验逻辑、deletedAt=null 过滤、错误码命名规则、软删除恢复时的唯一性再校验全部藏到实现里。9 个新 service 通过它完成软删除操作，自己只声明"哪个 model、哪个字段、哪个错误码前缀"。

Benefits

  • • Locality：软删除与唯一性语义改一处即全模块生效（例如未来引入复合唯一约束 @unique([name, deletedAt]) 时，只改 SoftDeleteService 的 assert 逻辑）
  • • Leverage：9 个新 service + 现有 PermissionsService 共 10 个调用方共用一个 adapter
  • • 测试：interface 是 test surface——只需对 SoftDeleteService 写一组并发/冲突/恢复场景测试，不必在每个 service 里重复测软删除分支
  • • 错误码命名规则（{MODULE}_{FIELD}_DUPLICATED_SOFT_DELETED）从约定变成代码，AI/人都不会拼错
Before — 9 份复制
After — 1 个深 module

9 个 service 不再持有软删除逻辑，只持有业务规则。Depth = 大量行为藏在 3 方法 interface 之后。注意：这要求 design.md D4 改写，tasks.md 2.x/3.x/4.x/5.x 的"service 实现软删除校验"改为"调用 SoftDeleteService"。

候选 2：InquiryNo 生成器抽为独立深 module

Worth exploring

Files

design.md D5 / tasks 4.2：当前计划把 generateInquiryNo() 作为 InquiriesService 的一个方法。

Problem

这段逻辑本身是深的（pg_advisory_xact_lock + 当月最大序号 + 3 次重试 + 候选号生成），但它混在 InquiriesService 里，与 CRUD 逻辑共用一个 interface。interface 是 test surface——要测并发冲突重试，得通过 InquiriesService.create 绕一大圈，locality 差：并发 bug 藏在 create 的某行里，与"创建询价单"业务规则混在一起。

Solution

抽出独立 module InquiryNoGenerator（src/modules/inquiry/inquiries/inquiry-no.generator.ts），interface 仅 next(): Promise<string>。InquiriesService.create 注入它，事务内调 generator.next() 拿编号后写入。生成器的并发/重试/锁逻辑全部藏在实现里，有独立 test surface。

Benefits / 取舍

  • • Locality：并发重试逻辑集中在 Generator，bug 改一处；InquiriesService 只剩询价业务规则
  • • 测试：可直接对 Generator 写并发场景（mock Prisma 抛唯一约束冲突），不必起完整 InquiriesService
  • • 取舍：多一个文件。但 Generator 的 interface（1 方法）极小，depth 高，值得抽
  • • 未来若改 DB 序列方案（design.md D5 替代方案），只换 Generator adapter，InquiriesService 不动——两个 adapter 才是真实 seam，目前虽只有一个，但并发生成编号天然是可替换策略
Before — 混在 InquiriesService
After — 抽出 Generator

候选 3：BaseService 的 4 个 paginate 变种合并

Worth exploring

Files

src/shared/services/base.service.ts:L103-L259。10 个新 service 都会调用这些方法（design.md tasks 3.x/4.x/5.x 隐含）。属"邻近现有代码"——但新设计会让调用方翻倍，深化 leverage 翻倍。

Problem

4 个方法是 (是否排序?) × (是否包装响应?) 的排列组合：paginate / paginateWithResponse / paginateWithSort / paginateWithSortAndResponse。Large interface + thin implementation——每个变种实现就 2-3 行。deletion test：删掉 3 个变种，调用方传 options bag 即可，复杂度不回归 → shallow。

Solution

合并为单一方法 paginate<T>(model, opts: { pagination, where?, include?, orderBy?, defaultSortBy?, wrapResponse? }): Promise<...>。options bag 表达所有变种。保留旧 4 方法作 deprecated 薄壳调用新方法，逐步迁移。

Benefits / 风险

  • • Leverage：新 10 service + 现有 N service 都受益，interface 从 9 方法降到 7（去 4 留 1）
  • • Locality：分页/排序/响应包装逻辑一处维护
  • • 风险：触及现有 22 个 service 的调用方——需 grep 全仓替换或保留 deprecated 薄壳。建议本次只加新方法，新 10 service 用新方法，旧代码不动
  • • ADR 冲突：无；这是纯接口深化
Before — 4 变种
After — 1 方法 + options

候选 4：字典型 CRUD 模块（brands/catalogs/filter-types）共享 base

Speculative

Files

design.md tasks 3.1/3.2/3.3：brands / catalogs / filter-types 三个 service 几乎同构（name/code 唯一 + status + sortOrder + 软删除）。

Problem

这三个是典型字典 CRUD——service 几乎是 Prisma 透传。deletion test 模糊：删掉 BrandsService，controller 直接调 Prisma + SoftDeleteService（候选 1）后，复杂度几乎不回归。它们本就 shallow，但是否"深化"取决于能否抽一个 DictionaryCrudService。

Solution / 风险

可抽 DictionaryCrudService<T>，三个 service 只声明 model 句柄 + 唯一字段名 + 错误码前缀。但 风险：过度抽象——若未来 brands 需要"slug 生成"、filter-types 需要"引用计数"，base 会泄漏分支。三个 service 的 shallow 是"事实上的浅"，强行加 base 可能让 interface 变大但实现仍薄。

判定

仅当候选 1（SoftDeleteService）落地后，这三个 service 真的只剩 5 行 CRUD 时再考虑。当前建议：保留三个薄 service，依赖候选 1 吃掉软删除复杂度即可。shallow 但有候选 1 兜底，可接受。

顶级推荐

先做 候选 1（SoftDeleteService 集中化）。理由：

  1. 窗口期：design.md 尚未实现，D4 的"9 份复制"还没落地。现在改 design.md + tasks.md 一处文字，比落地后重构 9 个 service 便宜一个数量级
  2. 杠杆最大：9 个新 service + 现有 PermissionsService = 10 个调用方共用一个深 module
  3. 不阻塞：不触及现有 22 个 service 的调用方（除非主动迁移 PermissionsService，可后置）
  4. 与 ADR 无冲突：ADR-0001（PG 迁移）与本无关；ADR-0002（独立 Customer）不涉及软删除策略

候选 2（InquiryNoGenerator）可作为第二优先——它本身已是深逻辑，只是位置不对，抽出成本低、收益清晰。候选 3（BaseService 合并）建议本次只加新方法供新 service 用，旧代码不动，避免 scope 蔓延。候选 4 暂缓，等候选 1 落地后再评估。
